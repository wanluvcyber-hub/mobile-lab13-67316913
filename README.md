# Mobile Lab 13 — แอปบัญชีรายรับ-รายจ่าย (Provider + SQLite)

โฟลเดอร์ `expense_tracker_provider/` คือเฉลยปฏิบัติการบทที่ 13 ครบทั้ง
กระบวนการที่ 1–6, การบ้าน (หน้าฟอร์มเพิ่ม/แก้ไข) และความท้าทายเพิ่มเติมทั้ง 3 ข้อ

## วิธีรัน
```bash
cd expense_tracker_provider
flutter create .        # สร้างโฟลเดอร์ android/ios (ไม่ทับ lib/ และ pubspec.yaml)
flutter pub get
flutter run
```

## ความท้าทายเพิ่มเติม
**ข้อ 1 — คอลัมน์ note + onUpgrade**
`_dbVersion = 2`, `_onCreate` สร้างตารางที่มี `note` เลย (ผู้ใช้ใหม่), ส่วน `_onUpgrade`
ใช้ `if (oldVersion < 2) ALTER TABLE ... ADD COLUMN note TEXT` (ผู้ใช้เดิม) แถวเก่าจะมี note เป็น NULL
`fromMap` จึงอ่านเป็น `String?`
วิธีทดสอบ: ติดตั้งโค้ดที่ตั้ง version เป็น 1 (ลบ note ออกชั่วคราว) เพิ่มข้อมูล แล้วคืนโค้ดเป็น v2 รันทับโดยไม่ถอนการติดตั้ง ข้อมูลเดิมต้องอยู่ครบ

**ข้อ 2 — ยอดคงเหลือด้วย SUM**
```sql
SELECT COALESCE(SUM(CASE WHEN type = ? THEN amount ELSE -amount END), 0) AS balance FROM transactions
```
แสดงใต้ AppBar พร้อมบรรทัดเทียบกับยอดที่วนบวกใน Dart (`balanceFromDart`) ผลต้องเท่ากัน
ความต่าง: Dart ต้องโหลดทุกแถวขึ้นหน่วยความจำและสร้างอ็อบเจกต์ก่อนบวก ส่วน SQL ส่งกลับแค่ตัวเลขตัวเดียว
เมื่อมีหลายพันแถว SQL ใช้หน่วยความจำและการส่งข้อมูลข้ามแพลตฟอร์มน้อยกว่ามาก
(ในแอปนี้ยังโหลดรายการทั้งหมดมาแสดงอยู่แล้ว จึงเห็นความต่างชัดเมื่อใช้ SUM เดี่ยว ๆ โดยไม่ต้อง query รายการ)

**ข้อ 3 — นำเข้า 100 รายการ**
เมนู ⋮ มี 2 แบบ และแสดงเวลาที่ใช้ใน SnackBar
- ทีละรายการ: เรียก `addTransaction` 100 ครั้ง (แต่ละครั้ง insert + query ทั้งตาราง + SUM + notify)
- batch: `transaction()` + `batch.commit(noResult: true)` แล้วโหลดรายการครั้งเดียว
ผลที่คาดหวัง: batch เร็วกว่าหลายเท่า เพราะเขียนดิสก์ครั้งเดียวและข้ามจาก Dart ไปฝั่งแพลตฟอร์มรอบเดียว
(ตัวเลขจริงขึ้นกับเครื่อง ให้จดผลที่ได้ลงตารางด้านล่าง)

## คำถามชวนคิด 13.12 (แนวคำตอบ)

**1) provider สองตัวใช้ DB ไฟล์เดียวกัน แบบไหนดีกว่า?**
แบบ `DatabaseHelper` Singleton ดีกว่า เพราะเปิดไฟล์ครั้งเดียว มีที่เดียวที่ดูแล `onCreate`/`onUpgrade`
และทุกคำสั่งเข้าคิวผ่านการเชื่อมต่อเดียว ถ้าให้แต่ละ provider เปิดและสร้างตารางเอง โค้ด schema จะกระจายและแก้ version ไม่ตรงกันได้
การทดสอบโดยไม่แตะไฟล์จริง: แบ่งชั้น `Provider → Repository (interface) → DatabaseHelper`
ใน test สร้าง `FakeRepository` ที่เก็บข้อมูลใน List หรือใช้ `sqflite_common_ffi` เปิด DB แบบ `inMemoryDatabasePath`
แล้ว inject เข้า provider ผ่าน constructor

**2) สองเครื่องแก้รายการเดียวกันตอนออฟไลน์ ข้อมูลเครื่องไหนเป็นฉบับจริง?**
ไม่มีคำตอบเดียว ขึ้นกับชนิดข้อมูล
- ใครต่อเน็ตก่อนชนะ: ง่ายแต่ผู้ใช้อาจเสียการแก้ไขที่ใหม่กว่า
- Last-write-wins ด้วยเวลาแก้ไข: ตรงกับเจตนาผู้ใช้มากกว่า แต่นาฬิกาเครื่องเชื่อถือไม่ได้ (ผู้ใช้ตั้งเวลาเองได้ เขตเวลาผิดได้)
  ควรใช้เวลาของเซิร์ฟเวอร์ตอนซิงก์ หรือเลขเวอร์ชันต่อแถว (เช่น `version` / `updated_at`) แล้วตรวจก่อนเขียนทับ
- ผสานระดับฟิลด์ หรือถามผู้ใช้เมื่อชน: ปลอดภัยที่สุดสำหรับข้อมูลสำคัญอย่างบัญชีเงิน
สำหรับแอปการเงิน แนะนำให้เก็บเป็น "รายการเพิ่มต่อท้าย" (append-only) แทนการแก้ทับ จะชนกันน้อยลงมาก
